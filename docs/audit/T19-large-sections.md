# T19 四个 >1MB 单节性能评估

- 日期：2026-11-10
- 状态：评估完成；**未做拆分/重写**
- 背景：T03 一直有 4 个 >1MB 单节 warning；Phase 5 需要决定是否二次拆分。

## 1. 实测对象

| 节 | 标题 | 原始大小 | gzip | 一页 DOM 节点数（1440 视口） |
|---|---|---:|---:|---:|
| c08-s3 | 奇异值分解 | 1.19 MB | 60.5 KB | 94,665 |
| c22-s1 | 先验、似然与后验 | 1.07 MB | 56.9 KB | 90,312 |
| c14-s2 | 弱收敛的刻画与运算法则 | 1.06 MB | 59.7 KB | 93,773 |
| c30-s1 | 状态空间表示 | 1.05 MB | 57.9 KB | 87,361 |

对比：普通节 gzip 约 10–30KB，DOM 通常数千到一万级。

## 2. 实测结果

- 四页均无横向溢出（`scrollWidth <= clientWidth`）；
- 深链标题定位正常（`top` 134/170px）；
- 首屏 gzip 仍只有 57–60KB，网络不是瓶颈；
- 主要成本是 **DOM 节点 8.7–9.5 万**，来自长节 + 大量环境块 + 构建期 KaTeX 的 HTML+MathML 双份标记；
- 本次 Chrome 长任务观察器未捕获到 >50ms 条目，但不等于低端手机会流畅；未做真机验证。

## 3. 结论

这 4 节的问题是 **DOM 规模**，不是下载体积。直接按“1MB 就拆”会破坏节锚点、搜索定位、学习状态粒度与习题归属，代价高于收益。

## 4. 候选优化（按风险排序）

1. **保留现状 + 真机监测**（当前选择）：先用低端 Android/iPhone 实测滚动、首屏、内存；没有明显卡顿就不拆。
2. **`content-visibility: auto` + 合理 `contain-intrinsic-size`**：降低离屏环境块的布局/绘制成本，DOM 仍在；需测滚动条跳动与打印。
3. **把 KaTeX 输出改为 `html` 单份**：可减少节点，但失去 MathML 可访问性；不建议在未做屏幕阅读器测试前采用。
4. **节内二级懒渲染**：按环境块分片挂载，改动 Reader 渲染架构，风险最高。
5. **拆分节**：会改变 URL/锚点/状态/习题归属，需内容模型迁移，暂不采用。

## 5. 建议验收口径

- 低端移动设备首屏可读 <3s、滚动无明显掉帧、无内存崩溃；
- 若仅桌面流畅，仍可接受，但需在 README 标注“4 个超长节在低端设备可能较重”；
- 不做为了指标的盲目拆分。
